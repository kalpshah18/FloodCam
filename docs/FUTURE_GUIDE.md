# FloodCam: guide for continuing the project

Written 2026-10-29 for Kalp and for any later Claude session. Read this first, then `CLAUDE.md`
(original brief; partly superseded, see section 1) and `docs/DECISIONS.md` (why things are the way
they are). Every reported number lives in a generated file under `results/`; this guide points at
them and deliberately contains no metrics.

## 1. Where the project stands

**Question:** can water depth near a reference object be read from a fixed camera well enough to decide
whether a 3 cm threshold is exceeded, and how does error depend on resolution (cm/pixel) and image
quality?

**What was done**

| Track | Status | Where |
|---|---|---|
| Synthetic generator, HSV baseline, calibration, temporal filter, state machine, SQLite store, dashboard, SegFormer training scripts | built (milestones 1-8 of the original plan) | `src/floodcam/{synth,calib,depth,temporal,store,seg}`, `app/dashboard.py` |
| Upload-a-video dashboard (click two marks, change-vs-dry-reference reading, shake compensation, annotated video export) | built, validated on synthetic video only | `app/upload_view.py`, `src/floodcam/live.py` |
| **Real-footage study** on USGS gauge cameras with official gauge labels | built and evaluated on one site | `src/floodcam/real/`, `scripts/real_*.py`, `results/real/` |
| Production model for that site | trained, committed (0.2 MB) | `models/in_overland/` |
| Real data beyond one site, tape-measured 3 cm data | **not done** | sections 5 and 9 |

**Pivot:** the original brief assumed self-collected tray data and synthetic-first development.
No real data existed, so the reported results now come from real USGS footage instead. The synthetic
data remains only for unit tests and dashboard demos. Where `CLAUDE.md` and this guide disagree
(for example "Never use synthetic in results" still holds; "SegFormer is Candidate 1" no longer
leads), this guide and `docs/DECISIONS.md` win.

**Headline files (open these for numbers)**

- `results/real/SUMMARY.md`: all tables, generated by `scripts/real_report.py`.
- `results/real/figures/`: scatter, per-month error, risk-coverage, resolution, time series.

## 3. How the real-footage pipeline works

```
USGS frame (public S3)            gauge height (truth CSV)
        |                                  |
   resize to 1280 px                       |
        |                                  |
 SIFT registration to best of 13 reference views   (plate.py)  -- fails -> reuse last good pose (causal)
        |                                  |
 rectify plate quad -> strip (360 x 48 px, row 0 = top of plate)
        |                                  |
 per-row features (colour change vs dry template, texture, context, quality)  (reader.py)
        |                                  |
 per-row "submerged?" probability  <--- labels: row height < gauge reading (no hand labelling)
        |
 monotone change-point decode -> water level -> affine calibration -> cm
        |
 quality gate (Laplacian variance of the whole frame within [0.55, 1.7] x training median)
```

Why each piece exists (details in `docs/DECISIONS.md`):

- **Registration.** The camera pose changes between months. One reference failed on many frames, so
  there are 13 references (one per dev month) plus a causal fallback.
- **Learned row classifier.** A fixed colour threshold failed on infrared, glare and shadow frames
  (that is the baseline in the results).
- **Gate.** Frames with a very low Laplacian variance (fog, blur, mud on the lens) and very high
  variance (droplets, dirt, spray) read badly. Reporting coverage next to error is part of the result.
- **Plate bottom limit.** The plate starts at about 4 cm above the datum, so smaller depths read as 0.

### Using the trained model in code

```python
import cv2
from floodcam.real.infer import PlateModel, PlateStream

model = PlateModel.load("models/in_overland/reader.joblib")
r = model.read(cv2.imread("some_frame.jpg"))
print(r.status, r.depth_cm, r.margin)          # status: ok | rejected_quality | unregistered

stream = PlateStream(model)                    # for a time-ordered sequence
for img in frames:
    reading, median_depth = stream.update(img)  # causal pose fallback + median of last 5 accepted
```

The production model has seen the locked test blocks. Never quote its in-sample error as performance;
the held-out numbers in `results/real/` come from models trained without the evaluated months.

## 4. Rules that keep the results defensible

1. **Split by block (month/event/session), never by frame.** The locked blocks (2025-04, 2026-04) are
   fixed in `scripts/make_usgs_splits.py`. Do not tune on them. One disclosed exception exists: the
   gate was redesigned after a first locked look; both runs are logged (see `docs/DECISIONS.md`).
2. **Fit everything on training blocks only**: dry template, classifier, calibration, baseline
   threshold, gate thresholds (`fit_models` in `experiment.py`). Registration references come from dev
   blocks and use geometry only.
3. **Uncertainty is the spread across held-out blocks** (block bootstrap in `metrics.py`), not
   frame-level intervals. With one camera, effective n is the number of blocks.
4. **Every number comes from a script and a saved file.** `real_report.py` regenerates all tables.
5. **Report coverage with error** whenever the quality gate is used.
6. Synthetic data never appears in reported results. Tag any synthetic artifact `synthetic=true`.
7. Locked-test discipline: `real_final_test.py` logs each run in `final_test_log.jsonl`.

## 5. Adding more data (the most valuable next step)

### 5.1 More USGS cameras (needs the network allow-list change in `docs/DATA_SOURCES.md`)

`data/usgs/cameras.csv` lists all 1,353 cameras in the public image bucket; 34 look like staff gauges,
including a dozen shallow-flow sites. For each new camera:

1. **Labels.** Get gage height at the frame times. With `waterservices.usgs.gov` reachable:
   `https://waterservices.usgs.gov/nwis/iv/?sites=<site_no>&parameterCd=00065&startDT=...&endDT=...&format=json`
   (parameter 00065 = gage height, feet). The USGS station number is in the overlay text on the image
   (e.g. 411229084541101). Write `data/usgs/truth/<site>_gauge.csv` with columns `file,time,gage_ft`
   (`file` = image file name, `time` = UTC ISO). Match each frame to the nearest gauge value within
   20 minutes (see `stage_at` in the stagesight repo for a reference implementation).
2. **Frames.** Add the camera folder name to `CAMERAS` in `scripts/build_usgs_dataset.py`, run it.
3. **Geometry.** Create `configs/sites/<site>.yaml` (`reference`, `quad` TL,TR,BR,BL as 0-1 fractions,
   `top_ft`, `bottom_ft`, `reg_region`). Pick a clear daytime reference frame, copy it to
   `models/<site>/ref_main.jpg`, estimate the quad by eye, then run
   `python scripts/preview_plate.py --site <site>` and iterate until strips from different months show
   the tick labels at the same rows. Use `top_ft/bottom_ft` from the labels visible at the strip's
   top and bottom rows; the affine calibration fitted on training blocks absorbs small errors.
4. **Splits.** Add the site and its locked blocks to `LOCKED` in `scripts/make_usgs_splits.py`
   *before looking at any result*. Pick locked blocks from different seasons and include a real
   event.
5. **Run** `build_refs.py`, `extract_strips.py`, `real_cv.py --site <site>`, then `real_final_test.py --site <site>` once.
   `real_report.py` currently hard-codes `SITE = "in_overland"`; make it loop over sites when a
   second site exists.

### 5.2 Pooling sites and transfer

Once two or more plate cameras exist: (a) train one pooled model with leave-one-site-out evaluation
(the claim that matters most for "works on new cameras"), (b) test zero-shot transfer from in_overland
to the sibling overland-flow sites (same plate design), (c) fine-tune with a few labelled days and
plot error vs number of labelled frames. Row features are plate-relative, so the pooled model needs no
architecture change; add a `site` feature only if needed.

### 5.3 Other published datasets

Download recipes and licences are in `docs/DATA_SOURCES.md`. Each has a different shape, so write one
small adapter per dataset that outputs the same `manifest.jsonl` rows (`site,file,path,time,gage_ft,
gage_cm,is_ir,synthetic`), then reuse the rest of the pipeline.

### 5.4 Your own recording (strongest for the 3 cm question)

Follow `docs/RECORDING_PROTOCOL.md`: a marked pole in a tray or controlled patch, depths 0/2/3/5/10/20 cm
by tape, at least three scenes with different lighting and backgrounds, no people. Use the dashboard's
upload mode to calibrate (click the pole base and a known mark) and add a manifest row per frame with
the tape depth. This is the only route to tape-measured labels at the threshold; the USGS labels are a
gauge beside the plate and the plate bottom sits near 4 cm. For these videos use the upload-mode reader
(`floodcam.live`, change-vs-dry-reference) as the starting point, and train a row classifier the same
way as for USGS once there are enough frames per scene.

## 6. Improving the model

Ordered by expected value:

1. **More sites** (5.1) beats any modelling change.
2. **Gate and confidence.** The gate is a hand-built rule. Try a learned abstain (use the decode margin,
   registration inliers and frame statistics) and report the risk-coverage curve
   (`results/real/figures/risk_coverage_cv.png` is the starting point).
3. **Registration.** Frames that fail SIFT borrow an old pose; a plate-specific detector (the plate is a
   bright cream rectangle with a tick pattern) or ECC refinement of the borrowed pose would help in
   fog, infrared and washed-out frames. Measure by registration success vs month.
4. **Sub-4 cm range.** Depth below the plate bottom is invisible on the plate. Options: a second cue
   (the water edge on the floor/panel behind the plate, or reflections), or accept the floor and report
   it. This directly limits the 3 cm claim.
5. **Neural model.** A small CNN or SegFormer on the strip or on the whole frame needs torch
   (`pip install torch` pulls a large CUDA build in this sandbox; use a CPU wheel index or a GPU box,
   see `docs/TRAINING_AWS.md`). Compare against the gradient-boosting reader on the same blocks.
6. **Temporal model.** Readings are 15-60 min apart; `real/events.py` has a causal median and
   hysteresis episodes. A Kalman/monotone-rise prior would remove isolated outliers further.
7. **Night/infrared.** They share the model with a flag feature; a separate model per modality may help.

## 7. Research-question checklist for the report

(The paper is written later, from this repo. Suggested mapping from question to evidence.)

| Question | Evidence in the repo |
|---|---|
| Accuracy vs resolution (cm/pixel) | `results/real/resolution-*/summary.json`, `figures/resolution.png`; cm/px is computed from the plate quad in `scripts/real_resolution.py`. State that registration is done at native resolution (decision in `DECISIONS.md`) |
| Derived vs measured error | the error-model fit in the same summary (sigma_v and floor); explain that RMSE includes outliers and the floor is mostly gauge-plate offset and unreadable frames |
| Segmentation quality vs depth error | the baseline (threshold) vs learned comparison; the original mask-erosion experiment was not repeated on real data (open item) |
| 3 cm reliability | per-bin MAE, "near 3 cm" MAE, flood-at-3 cm precision/recall/false-alarm rate, plus the plate-bottom limit |
| Failure modes | `results/real/failures/` and `failures.csv` (blur, dirt, glare, infrared, pose change) |
| Temporal / events | `results/real/tables/event_level.csv` (the Flood/Recovering state machine is a demonstration, not an evaluated claim) |
| Generalisation | only across months of one camera so far; state it plainly and propose 5.1/5.2 |

Claims to avoid: validity on other cameras, on tape-measured depth, below 4 cm, at night with confidence,
or of the upload mode on real video.

## 8. Working with Claude on this repo

- Start a session by pointing at this file. Useful prompts: "Add USGS site X (steps in FUTURE_GUIDE 5.1)",
  "Rerun the report after new data", "Write the related-work section from DATA_SOURCES.md".
- Claude's cloud sandbox: Python 3.13, 4 cores, ~15 GB RAM, no GPU, network limited to GitHub, PyPI
  and the public USGS image bucket. Loading data from other hosts needs the allow-list change.
- Gotchas learned the hard way:
  - `pkill -f "<pattern>"` inside a command that contains the pattern kills the calling shell. Use `pgrep`
    with a bracketed pattern (`pgrep -f "[s]treamlit"`) or the PID.
  - Streamlit caches imported helper modules; restart the server after editing `app/*.py` helpers.
  - Downloaded data is untrusted: read it with `python -I` from outside its directory.
  - The `data/usgs/frames` folder is ~1 GB and ignored by git; rebuild with the scripts.
  - Registration is the slow step (about 8 min, 4 cores); the resolution sweep reuses it.
- Conventions: small commits, one step each; generated results are committed (they are small);
  log decisions in `docs/DECISIONS.md` and runs in `docs/EXPERIMENT_LOG.md`; cite external code
  and data in `AI_USE.md`.

## 10. Quick troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| `build_usgs_dataset.py` returns 0 frames | bucket unreachable (check `curl -I https://usgs-nims-images.s3.amazonaws.com`) or camera name wrong; compare with `data/usgs/cameras.csv` |
| Many `unregistered` frames | camera moved or new epoch: add a reference with `build_refs.py`, or look at `preview_plate.py` strips |
| Strips look shifted or squashed | quad corners wrong in `configs/sites/<site>.yaml` |
| CV error much worse than before | `data/usgs/strips/*.npz` out of date relative to the config; re-run `extract_strips.py` |
| Dashboard "Real USGS footage" empty | run `real_cv.py`, `real_report.py`, `make_real_demo.py` |
| Tests fail on a clean clone | the real-footage tests need only committed files (demo bundle, model, splits); upload-mode tests render synthetic video and need OpenCV with an mp4 encoder |
