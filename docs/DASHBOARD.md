# FloodCam Dashboard

## How to run

```bash
# 1. Generate synthetic demo data (if not already done)
make run-demo-multi

# 2. Launch dashboard
streamlit run app/dashboard.py
# or equivalently:
make dashboard
```

The dashboard opens at `http://localhost:8501`.  
The default DB path is `results/demo.db` (generated by `run-demo-multi`).

To point at a different DB:
```bash
streamlit run app/dashboard.py
```
Then edit the **DB path** field in the sidebar.

## Panels

### Sidebar controls

| Control | Description |
|---------|-------------|
| DB path | Path to a SQLite event DB on disk. |
| Run | Choose a recorded run from the `runs` table. |
| Camera | "all" shows every camera; choose one to filter all panels. |
| Live mode | Polls the DB every 5 s for new rows (use while a run is active). |
| Replay / Cursor | Scrub through a finished run to replay it at 1×, 10×, or 60× speed. |

### 1. Camera Status

Live state per camera at the cursor timestamp. Displays:

- **State**: Normal / Pending / Flood / Recovering — with ⚠ stale marker if the stream has a gap.
- **Severity**: colored chip AND text label (Advisory / Warning / Severe / Critical).
  The color uses the Okabe-Ito colorblind-safe palette; the text label is always present.
- **Depth** (cm), **Confidence** (0–1), **Rate of rise** (cm/10 min), **Last update** timestamp.

### 2. Depth Time-Series

Altair chart per camera. Features:
- Shaded state bands (Normal = green, Pending = yellow, Flood = orange, Recovering = blue).
- Dashed horizontal lines at 2.5 cm (clear), 3.5 cm (trigger), and severity boundaries 3, 10, 25, 50 cm.
- Main depth line (blue).
- Cross (×) markers for invalid samples (health fault frames, `valid=0`).
- Triangle (▲) markers for low-confidence samples (`confidence < 0.5`).
- Diamond (◆) markers at alert timestamps.
- Fully interactive (zoom/pan).

### 3. Annotated Frame

JPEG snapshot saved by the runner at the cursor position.
Shows: mask overlay (blue tint), waterline (cyan), depth and state text.
Placeholder message if the snapshot file is missing from disk.

### 4. Alert Log

Table of all alerts up to the cursor:
timestamp, camera, transition, severity class, depth.
Transition strings use `->` notation (e.g. `Normal->Pending`).

### 5. Camera Health

Per camera: current frozen / black / obstructed / offline flags, last healthy timestamp,
fault count for the run, and the check detail string from the health row.

## What each number means

| Field | Source | Notes |
|-------|--------|-------|
| `depth_cm` | Temporal filter output (rolling median) | Not raw depth; outliers smoothed |
| `confidence` | Waterline detector (continuity × coverage × resolution) | < 0.5 = low-conf |
| `rate_cm_per_10min` | OLS slope over `trend_window_minutes` | None if < 3 samples |
| `state` | Flood state machine | See DECISIONS.md for transition rules |
| `severity_class` | Depth + optional rate escalation | Advisory/Warning/Severe/Critical/Normal |
| `stale` | Gap > `max_gap_seconds` detected | No transitions fire when stale |

## Synthetic data banner

When the selected run has `synthetic=1` in the DB, a persistent yellow banner appears:

> **SYNTHETIC DATA — pipeline validation only.**  
> These results must not be cited in any paper or evaluation.

This banner is always shown for runs generated by `run_demo.py` or `run_demo_multi.py`.

---

## Draining-vs-accumulating logic (Recovering state)

The Recovering state on the dashboard is a **demonstration only**.  It is not a validated
claim.  Short synthetic clips (< 5 min) cannot validate the minutes-long draining trends
required to confirm a genuine Recovering transition.  See DECISIONS.md and CLAUDE.md for
the full reasoning.

No headless browser tooling (`playwright`, `selenium`) is installed in this environment.
